About Me

My path from operations into cybersecurity

My path to cybersecurity began in operations. I worked at Honeywell and now serve as an Operational Excellence Specialist at PIP Global Safety. Solving process problems taught me to observe carefully, assess risk, document decisions, and help teams adopt reliable ways of working.

My cybersecurity education wasn't a career restart; it was an extension of work I was already doing. Supporting internal audits and reviewing access controls alongside IT and security teams gave me a front-row seat to how security actually functions inside a real operation. Earning my Bachelor of Science in Cybersecurity from Franklin University let me formalize that knowledge: network security, cryptography, risk frameworks, and hands-on lab work with the tools security teams use every day.

I completed my degree while working full-time, graduating Summa Cum Laude with a 3.94 GPA. Before that, I earned my Associate of Science in General Science at Columbus State Community College, where I was inducted into the Phi Theta Kappa Honor Society.

Leadership philosophy

I believe the best process — or the best security control — is the one people actually follow, not the one that looks best on paper. That means involving the people doing the work in designing the solution, communicating clearly about why a change matters, and following through after rollout.

Continuous learning

Beyond my degree, I've pursued additional coursework in secure coding, Python for cybersecurity, and AI's role in risk and security — and I'm currently working toward CompTIA Security+.

Why this strengthens my cybersecurity capabilities

See how the disciplines connect

In operations, I observe a failure, preserve the facts, find its cause, change the process, and check whether the change holds. Security investigations follow a similar discipline: collect evidence, determine scope and cause, document a response, and verify the control. SOPs make both workflows repeatable; audits and metrics show whether the practice matches the written procedure. My technical security training adds the domain knowledge needed to apply that discipline to systems and alerts.

AI & Innovation

Honest about where I am with AI

Genuinely interested, actively learning, and not claiming production experience I don't have.

Why I'm learning AI

I saw AI start to reshape both of the fields I work in — process improvement and cybersecurity — and I wanted to understand it well enough to use it responsibly rather than react to it. In security, AI is increasingly used for anomaly detection, alert triage, and threat-intel summarization. In Operational Excellence, it has real potential in root-cause pattern-finding. I see these as the same underlying skill — using data to find the real problem faster — applied with a new tool.

Responsible AI principles

Human review before any AI-assisted output is trusted or acted on; transparency about what is and isn't AI-generated; awareness that AI tools can produce confidently wrong answers, which matters enormously in a security context.

Where I want to apply it (ideas, not completed projects)

  • AI-assisted log triage to help prioritize SIEM alerts
  • AI-based pattern recognition applied to recurring root-cause categories in OE data
  • Using AI tools to accelerate first-draft SOP and security-policy documentation, with human review as the final control

Verified relevant coursework: Generative AI – Risk and Cyber Security Masterclass (Udemy); AI concepts covered in the Franklin University Cybersecurity curriculum.

Home Lab — Build & Deployment

Standing up a SOC environment from scratch

An eight-week, self-directed build of an isolated home lab — firewall, domain, logging, and an attacker box — documented milestone by milestone rather than presented as a finished product.

1. Perimeter & Core

pfSense, Windows Server AD/DNS, one client

pfSense firewall, Windows Server (AD/DNS), and one Windows client stood up first — the deliberate build order, before any logging or detection tooling goes in.

2. Logging Layer

Wazuh / Security Onion added next

Wazuh/Security Onion added next, so every subsequent machine on the network is logging from the moment it joins — nothing added blind.

3. Segmentation

Ubuntu server + Kali on isolated segments

Ubuntu server and Kali attacker box join on isolated network segments, keeping offensive tooling walled off from the domain.

4. Detection & Response

Real alerts replace synthetic test data

Real Wazuh/Security Onion alerts feed the triage workflow — replacing the synthetic data used to build and test the tooling ahead of the lab going live.

5. Documentation

A running build journal, milestone by milestone

Every milestone logged in a running build journal — what shipped, why it was sequenced that way, and how it ties back to the lab's end goal.

6. End-to-End Case

Week 8 target: one real incident, start to finish

Week 8 target: one real incident carried start to finish — alert, correlation, manual investigation, report — on live lab telemetry instead of synthetic data.

Where the build stands right now

The SOC Alert Triage Tool was deliberately built ahead of sequence — against realistic synthetic alert data — so a tested, working tool is already in hand for the moment the logging tier goes live, rather than losing time building it after.
